# Exness Infrastructure

Two Terraform stacks plus a GitHub Actions pipeline deploy the whole platform
to AWS on every push to `main`.

```
infra/
├── bootstrap/   # one-time, run locally: state bucket + GitHub OIDC role
├── aws/         # main stack, applied by CI: ECR, VPC, EC2, SSM, S3
└── web/         # (pre-existing) optional OpenNext/CloudFront deploy of apps/web
```

## Architecture

Cost-first, production-sane. All six services (backend, engine, snap-shotting,
dbstorage, web, docs) plus Postgres, Redis, and MongoDB run as Docker Compose
on a single EC2 instance. Images live in ECR.

| Choice | Why |
| --- | --- |
| 1× EC2 `t3.medium` + EIP + ECR (~$35/mo) | ECS Fargate + RDS + ElastiCache + DocumentDB for the same stack is $300+/mo (DocumentDB alone starts ~$200/mo) |
| No NAT gateway | ~$32/mo saved; instance sits in a public subnet behind a strict security group |
| No SSH, no key pairs | Shell access via SSM Session Manager; deploys via SSM Run Command |
| GitHub OIDC | No long-lived AWS access keys stored in GitHub |
| Secrets in SSM Parameter Store (SecureString) | Never appear in Terraform outputs or CI logs; instance reads them at deploy time |
| ECR lifecycle policy (keep 10) | Image storage cost stays flat |

```
GitHub push (main, apps/mobile/** ignored)
  → checks: turbo check-types + build  --filter='!mobile'
  → terraform apply (infra/aws)        → creates/updates ECR, EC2, EIP, SSM params
  → docker build & push ×6             → ECR, tagged <git-sha> + latest
  → SSM Run Command on the instance    → deploy.sh: fetch secrets + compose file, pull, up -d
  → job summary                        → service URLs
```

## One-time setup

1. **Bootstrap (local, admin credentials):**

   ```sh
   cd infra/bootstrap
   terraform init
   terraform apply -var "github_repository=<owner>/<repo>"
   ```

   Note the two outputs: `tf_state_bucket` and `github_deploy_role_arn`.

2. **GitHub repository secrets** (Settings → Secrets and variables → Actions):

   | Secret | Value |
   | --- | --- |
   | `AWS_ROLE_ARN` | `github_deploy_role_arn` bootstrap output |
   | `TF_STATE_BUCKET` | `tf_state_bucket` bootstrap output |
   | `JWT_SECRET` | backend JWT signing secret |
   | `BETTER_AUTH_SECRET` | `openssl rand -base64 32` |
   | `GOOGLE_CLIENT_ID` | Google OAuth client ID |
   | `GOOGLE_CLIENT_SECRET` | Google OAuth client secret |
   | `USER_EMAIL` | nodemailer sender address |
   | `USER_PASSWORD` | nodemailer app password |

   Optional repository **variable**: `AWS_REGION` (defaults to `ap-south-1`).

3. **Push to `main`.** The pipeline provisions everything and prints the
   service URLs in the workflow run summary:

   - Web app → `http://<elastic-ip>:3001`
   - Backend API → `http://<elastic-ip>:8000`
   - Docs → `http://<elastic-ip>:3000`

   Pull requests run checks + `terraform plan` only; nothing is applied.

## Day-2 operations

- **Shell on the instance:** `aws ssm start-session --target <instance_id>`
  (instance ID is a Terraform output and shown in the workflow logs).
- **Database passwords** are generated by Terraform (`random_password`) and
  stored only in SSM under `/exness/prod/*`. Read one:
  `aws ssm get-parameter --name /exness/prod/POSTGRES_PASSWORD --with-decryption`.
- **Data durability:** Postgres/Redis/Mongo volumes live on the instance's
  encrypted root EBS volume. Snapshot it before replacing the instance
  (`user_data` changes recreate the instance!).
- **Rollback:** re-run the deploy job with an older image tag, or on the
  instance: `/opt/exness/deploy.sh <old-git-sha>`.
- **Teardown:** `terraform destroy` in `infra/aws` (state bucket and OIDC
  role from `bootstrap` survive).

## Mobile app

`apps/mobile` (Expo) is intentionally outside this pipeline: the workflow
ignores `apps/mobile/**` path changes, the CI build uses
`--filter='!mobile'`, and no Dockerfile copies the mobile app. Ship it with
EAS instead.

## Known trade-offs

- Plain HTTP on the Elastic IP. For HTTPS, point a domain at the EIP and put
  Caddy/nginx (or CloudFront) in front — also required before Google OAuth
  will work on a non-localhost origin.
- `docs.Dockerfile` still runs `next dev`; switch its CMD to `build` + `start`
  for lower memory and faster responses.
- Single instance = single point of failure. Acceptable at this budget; the
  whole stack is reproducible from Terraform + ECR in minutes.
